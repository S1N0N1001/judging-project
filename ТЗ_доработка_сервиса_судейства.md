# Техническое задание на доработку сервиса судейства

Версия: 1.0. Дата: 03.11.2026.

Статус: проект ТЗ для реализации. Решения, требующие утверждения методики, явно выделены в разделе 12. Написание этого документа не означает, что описанные функции уже реализованы.

## 1. Цель и исходное состояние

Довести существующее локальное приложение судейства до надёжной работы на мероприятии: защитить административный доступ, исключить потерю оценок, сделать процедуру расчёта воспроизводимой, заменить основной TXT-экспорт табличным CSV и обеспечить запуск на Windows через EXE без установки Python пользователем.

Основа: `main.py`, `config.json`, `db.json`, `.streamlit/config.toml`, `документация.txt`; документы `mvp.md`, `lik_bez.md` и статья о многокритериальной методике. При расхождении описаний фактическое исходное поведение устанавливается по коду. MVP рассматривается как ориентир, а не как требование буквально воспроизвести старый интерфейс.

Уже существуют: панели секретаря и судьи, команды, ссылки и QR судей, семь критериев на 100 баллов, дескрипторы, запись в JSON, переоценивание, таблицы прогресса и результатов, расчёт и TXT-отчёт.

## 2. Границы работ и приоритеты

| Приоритет | Состав | Условие готовности |
|---|---|---|
| P0: до официального использования | Доступ, транзакционное хранение, безопасная правка, фиксация методики, валидация, состояния мероприятия и блокировка | Нельзя получить права секретаря без авторизации; сохранённые оценки не теряются; окончательный результат воспроизводится |
| P1: обязательная поставка | CSV, журнал, резервирование, миграция, EXE, документация и приёмочные проверки | Организатор запускает приложение без Python и получает полный табличный протокол |
| P2: последующее развитие | Автономная очередь на телефоне, PWA, расширенная аналитика, печатный протокол | Отдельная итерация после пилота |

Сохранять Streamlit, если он обеспечивает требования P0/P1. Переписывание на другой стек не является самостоятельной целью. Полноценная работа без связи на стороне телефона в текущую поставку не входит; интерфейс обязан честно показывать, какие данные ещё не сохранены.

## 3. Роли и доступ

### 3.1. Секретарь

- Открытие адреса без кода показывает экран входа, но не выдаёт административную роль или секрет.
- При первом локальном запуске секретарь создаёт пароль через процедуру первоначальной настройки, доступную только с ноутбука сервера. Удалённый клиент не может первым захватить настройку.
- Для настройки использовать одноразовый случайный секрет, передаваемый лаунчером локально; после настройки он аннулируется. Не сохранять его в CSV, журналах или постоянных ссылках.
- Пароль хранить в виде стойкого хеша с солью; не хранить открытый пароль. Ограничить частоту неудачных входов. Предусмотреть выход и документированное локальное восстановление доступа без удаления оценок.
- После входа хранить авторизацию в сессии. Проверять права в операциях изменения данных, а не только при отображении панели.

### 3.2. Судья

- Индивидуальный случайный токен, генерируемый через `secrets`, привязан к постоянному `judge_id` и мероприятию.
- Перевыпускать доступ одному судье без изменения чужих ссылок и оценок. Старый токен становится недействительным, в том числе для уже открытой сессии при следующей операции.
- Номер места является отображаемым атрибутом, а не идентификатором владельца оценок. Замена человека создаёт нового судью; перенос старых оценок автоматически запрещён.
- Судья получает только свои оценки. Чужие оценки и служебные токены не должны попадать в его страницу, сообщения или загрузки.
- Проверять актуальность доступа при каждой записи. Исключить утечку токенов в диагностические логи.

### 3.3. Настройки сети

Проверить работу со штатной XSRF-защитой и ограниченным набором разрешённых origin. Не отключать защиту глобально ради подключения телефонов. Проверить сценарии доступа как с localhost, так и по выбранному адресу LAN.

## 4. Хранение и целостность

### 4.1. SQLite

Заменить рабочую JSON-базу на SQLite. Обеспечить транзакции, внешние ключи, обработку временной занятости базы и соединения, корректные для параллельных сессий. Базу хранить на локальном диске сервера, не на общей сетевой папке.

Минимальные сущности:

| Сущность | Основные данные |
|---|---|
| event | ID, название, дата, статус, текущая работа, версия и снимок методики |
| participant | ID, номер/порядок, название работы или команды, участники, аннотация, тип, стадия, материалы |
| judge | Постоянный ID, номер, статус, данные доступа |
| scorecard | Судья, работа, состояние, версия, время сохранения и отправки |
| score | Оценочная карточка, критерий, числовое значение |
| penalty | Работа, величина, причина, подтверждение, автор и время |
| audit | Время, пользователь, действие, объект, причина и изменения |

Уникальность: одна актуальная карточка на пару «судья + работа»; одна оценка критерия на карточку. Историю правок хранить отдельно от актуальных значений.

### 4.2. Правила записи

- Сохранять карточку целиком в одной транзакции; частично записанная карточка невозможна.
- Проверять наличие всех обязательных критериев, числовой тип, допустимые границы, статус события и права автора.
- Использовать версию карточки для обнаружения конфликтов двух вкладок: устаревшая запись не перетирает новую молча.
- Повторная отправка одного действия не создаёт дубликатов.
- При переоценивании прежняя подтверждённая версия сохраняется до успешной записи новой. Отмена и разрыв связи не удаляют её.
- Опасные массовые действия требуют подтверждения; после начала оценивания вместо физического удаления использовать архивирование либо управляемый откат с причиной.
- Сокращение состава судей не должно молча менять официальный итог. Изменение состава после открытия оценивания требует отдельного подтверждения и записи в журнале.

### 4.3. Миграция и резервирование

- Перед импортом исходного `db.json` создать неизменённую резервную копию.
- Предусмотреть версию схемы, проверку данных, отчёт об ошибках и повторный запуск миграции без дублирования.
- Оценки, не соответствующие конфигурации, не исправлять и не отбрасывать молча: показать секретарю список проблем и запретить окончательный расчёт до решения.
- Выполнять резервное копирование при миграции, перед массовыми изменениями и при закрытии события; добавить ручную кнопку резервирования.
- Копировать открытую SQLite-базу через механизм согласованного backup, а не простым копированием одного файла при активной записи.
- Восстановление выполнять при остановленной записи, с проверкой целостности и сохранением предыдущей базы.

## 5. Процедура оценивания

Состояния события: `подготовка → оценивание → закрыто → утверждено`. Возврат к оцениванию возможен секретарём с причиной и журналированием; прежний утверждённый снимок остаётся в истории.

- В подготовке редактируются участники, судьи и конфигурация.
- При открытии фиксируется снимок критериев, максимумов, дескрипторов и алгоритма. Изменение глобального файла не переопределяет уже начатое событие.
- Секретарь назначает текущую работу. Судья видит её и ранее открытые работы; выбор вручную сохраняется. Автообновление не сбрасывает незаписанный ввод и не переключает его без предупреждения.
- До закрытия секретарь видит прогресс и статусы; числовые оценки скрыты. Это правило является предлагаемым вариантом независимого судейства.
- Карточка судьи имеет состояния `черновик → отправлена`. Отправка блокирует правку судьёй. Разблокировка доступна секретарю с обязательной причиной.
- Закрытие блокирует запись оценок на сервере, включая действия из ранее открытых вкладок. До закрытия показывать полноту отправки; закрытие при пропусках запрещать, пока секретарь не зафиксирует разрешённое регламентом исключение.
- В закрытом событии доступны числовые результаты и анализ расхождений. Утверждение создаёт неизменяемый снимок протокола.
- Оценка начинается с «не оценено», а не с автоматически выбранного среднего балла. Ноль является полноценной оценкой и отличается от отсутствия значения.
- Показывать все дескрипторы по запросу и текущий дескриптор рядом со шкалой. Согласовать границы критерия 5: в текущем коде 0/5/10/14, в `lik_bez.md` 0/5/9/13.
- Показывать время последнего успешного сохранения, состояние соединения и понятную ошибку. Нельзя показывать «сохранено» до подтверждения транзакции.
- Добавить необязательный комментарий судьи к работе; хранить отдельно от числовых баллов.

## 6. Методика расчёта

### 6.1. Версионирование

Выделить чистый модуль расчёта, независимый от Streamlit и файлового ввода-вывода. На одинаковом снимке исходных данных и конфигурации он выдаёт одинаковый результат.

Текущее поведение обозначить `legacy_total_trim_v1`: снятие одной минимальной и одной максимальной суммы судьи при трёх и более оценках; среднее оставшихся сумм. Сохранить его для воспроизведения старых результатов, но не выбирать скрыто для новых событий.

Предлагаемый режим `criterion_trim_v1`, требующий утверждения:

1. По каждому критерию взять оценки допущенных и отправивших карточку судей.
2. При пяти и более оценках удалить одно минимальное и одно максимальное значение отдельно по каждому критерию; при меньшем количестве использовать все допустимые значения.
3. Рассчитать среднее оставшихся значений.
4. Сложить средние семи критериев и вычесть утверждённые штрафы.
5. Округлить конечный результат до 0,01 по явно заданному правилу; промежуточные значения не округлять для вычислений. Отображаемые значения могут быть округлены отдельно.

Максимумы критериев уже задают их веса в 100-балльной шкале. Дополнительное умножение на эти максимумы запрещено. При специальных ограничениях по типам работ нельзя вводить скрытую нормализацию к 100.

### 6.2. Полнота и равенство

- Неполные результаты помечать как предварительные; не представлять их как официальный рейтинг.
- Отсутствующие оценки не заменять нулями.
- Один и тот же набор допущенных судей использовать в расчёте, детализации и CSV.
- Для равных результатов предусмотреть настраиваемое правило. Предлагаемый вариант: сравнение конечных баллов с точностью 0,01, одинаковые места по схеме 1, 2, 2, 4; порядок строк внутри равенства по номеру работы без влияния на место.
- В протоколе показывать используемый алгоритм, количество принятых оценок, снятые значения, исходный итог и штраф.
- Расхождение по критерию рассчитывать до снятия крайних; предлагаемый показатель — `(максимум − минимум) / допустимый максимум`. Порог утверждается до открытия события. Превышение требует решения секретаря, а не автоматического изменения оценок.
- Штраф требует подтверждённого основания и причины. Шкала и нижняя граница результата утверждаются отдельно. Пока параметры не заданы, штрафы отключены явно.

## 7. Экспорт CSV вместо основного TXT

### 7.1. Пользовательский сценарий

На вкладке «Итоги» разместить кнопки «Скачать сводку CSV», «Скачать оценки судей CSV», «Скачать расчёт по критериям CSV» и «Скачать полный протокол ZIP». ZIP содержит три CSV и файл метаданных JSON. Каждый CSV доступен отдельно.

CSV становится основным способом выгрузки. Кнопки сохранения `results.txt` убрать из основного сценария; при необходимости TXT оставить в дополнительном разделе совместимости. В интерфейсе добавить поиск команды, сортировку и фильтр по полноте оценивания.

Имена файлов: `results_<event_id>_<YYYYMMDD_HHMMSS>_summary.csv`, аналогично `_scores.csv`, `_criteria.csv`, `_protocol.zip`. Экспорт включает весь протокол независимо от текущего фильтра таблицы. Отдельный экспорт отфильтрованного набора возможен только с явной подписью.

### 7.2. Сводка: одна строка на работу

Порядок столбцов:

`Мероприятие_ID;Мероприятие;Статус_протокола;Работа_ID;Номер;Команда_или_работа;Участники;Тип_работы;Стадия;Место;Судей_ожидается;Судей_отправили;Полнота;Критерий_1;Критерий_2;Критерий_3;Критерий_4;Критерий_5;Критерий_6;Критерий_7;Итог_до_штрафов;Штраф;Итог;Алгоритм;Версия_методики;Снимок_ID;Сформировано`

- Значения критериев — агрегаты, действительно участвующие в расчёте. В режиме legacy, где это не выполняется, соответствующие поля оставить пустыми и дать сырые средние в отдельной детализации с явной маркировкой.
- Место заполнять только для официально ранжируемых работ. Предварительный балл разрешён с явным статусом.
- Участников объединять внутри одной CSV-ячейки, не создавать неоднозначные дополнительные строки.

### 7.3. Оценки: одна строка на пару «работа + судья»

`Мероприятие_ID;Работа_ID;Номер;Команда_или_работа;Судья_ID;Судья_номер;Статус_карточки;Критерий_1;Критерий_2;Критерий_3;Критерий_4;Критерий_5;Критерий_6;Критерий_7;Сумма_судьи;Комментарий;Версия_карточки;Сохранено;Отправлено;Допущен_к_расчёту`

Включать ожидаемые пары, даже если карточка отсутствует: пустые баллы, статус «не заполнена». Не экспортировать токены, пароли, хеши и административные ссылки. В окончательном протоколе исходные оценки должны позволять независимо пересчитать итог.

### 7.4. Детализация: одна строка на «работа + критерий + судья»

`Мероприятие_ID;Работа_ID;Критерий_ID;Критерий;Максимум;Судья_ID;Исходный_балл;Решение;Причина_исключения;Агрегат_критерия;Разброс;Требует_обсуждения`

Поле «Решение»: учтена / снята минимальная / снята максимальная / не допущена / отсутствует. При одинаковых крайних значениях выбор исключаемого судьи детерминирован по постоянному ID; это не меняет итог. Для legacy отдельно указывать, что исключение выполнено по сумме судьи, а не по критерию.

Метаданные полного протокола: версия схемы экспорта, снимок методики, максимумы и дескрипторы, алгоритм, состав жюри, решения об исключениях, правила округления и ничьих, перечень штрафов с причинами, статус и время утверждения. Секреты доступа исключить.

### 7.5. Формат и совместимость

- По умолчанию: UTF-8 с BOM, разделитель `;`, десятичная запятая, строки CRLF; целевая проверка — Excel с русскими региональными настройками и LibreOffice.
- Дополнительный профиль «универсальный CSV»: UTF-8 с BOM, запятая как разделитель, точка как десятичный знак.
- Формировать через CSV-библиотеку; кавычки, разделители и переносы внутри значений экранировать по правилам CSV.
- Ноль экспортировать числом, отсутствующее значение — пустой ячейкой. Не использовать символ «—» в числовых колонках.
- Даты: ISO 8601 с часовым смещением. Время мероприятия хранить с явным часовым поясом.
- Текстовые поля, которые табличный редактор может интерпретировать как формулу, обезвреживать при экспорте, включая опасные начальные символы `=`, `+`, `-`, `@` и управляющие префиксы. Числовые поля формировать только из проверенных чисел.
- Все файлы одной выгрузки формировать из одного согласованного снимка данных. Изменение оценки в другой сессии не должно приводить к разным итогам внутри одного ZIP.
- Окончательная выгрузка использует утверждённый снимок, а не пересчитывается по изменившейся конфигурации.

## 8. Поставка Windows и запуск через EXE

### 8.1. Рекомендуемое решение

Упаковать приложение и Python-зависимости с PyInstaller. Первая целевая поставка — `onedir`: папка приложения с `Judging.exe` и служебными ресурсами, распространяемая ZIP-архивом или установщиком. Пользователь запускает один EXE; отдельная установка Python, Streamlit и OpenServer не требуется. Все файлы папки поставки должны сохраняться вместе.

Это упаковка локального сервера и среды выполнения. После запуска EXE интерфейс работает в стандартном браузере; судьи подключаются к этому серверу со смартфонов. Ноутбук должен оставаться включённым.

Режим `onefile` рассматривать после стабильной сборки `onedir`: он удобен для передачи одним файлом, но распаковывает ресурсы во временную папку при старте. Рабочая база в этой папке храниться не должна. Один EXE не означает отсутствие постоянных файлов данных.

### 8.2. Лаунчер

Разработать отдельный `launcher.py`:

1. Проверить наличие уже работающего экземпляра этого приложения для текущего каталога данных.
2. Если экземпляр найден, открыть его адрес без запуска второго сервера; не считать любой ответ на порту признаком нашего приложения.
3. Определить каталог данных и проверить права записи.
4. Выбрать интерфейс и порт; по умолчанию порт 8501. Если занят посторонним процессом — предложить другой, не завершать чужой процесс.
5. Запустить сервер в управляемом процессе с закреплёнными настройками. В замороженной сборке предусмотреть отдельный режим запуска сервера: вызов `sys.executable -m streamlit` нельзя считать рабочим без специальной реализации.
6. Дождаться готовности HTTP-сервера с ограничением времени, после этого открыть браузер на `http://localhost:<порт>`.
7. Оставить небольшое окно управления: статус, «Открыть интерфейс», LAN-адрес, каталог данных, «Открыть журнал», «Остановить сервер».
8. При ошибке показать понятное сообщение и путь к журналу; не оставлять незаметный фоновый процесс.
9. Останавливать сервер корректно, завершая активные транзакции. Закрытие вкладки браузера не останавливает сервер. При закрытии окна лаунчера предлагать свернуть либо остановить; без бесконтрольного завершения.

В релизе скрыть консоль, но сохранить журналирование. Диагностическая сборка с консолью допускается отдельно.

### 8.3. Сеть

- Режимы: «Только этот компьютер» и «Локальное мероприятие». Во втором сервер слушает LAN; секретарь выбирает нужный интерфейс при нескольких адаптерах.
- Адрес QR судей формировать из выбранного LAN-IP и фактического порта. `0.0.0.0` и `localhost` не выдавать смартфонам как адрес подключения.
- Не полагаться только на определение маршрута через внешний IP: интернет на мероприятии может отсутствовать.
- Выводить инструкцию по разрешению входящего соединения в частной сети Windows; не отключать брандмауэр целиком и не открывать публичные сети автоматически.
- Добавить необязательную генерацию QR Wi-Fi из введённых SSID и пароля; создание самой точки доступа остаётся действием организатора по инструкции.
- Изменение адреса или порта требует обновления QR. Во время мероприятия менять их только с предупреждением.

### 8.4. Каталоги

- Ресурсы и исходный шаблон конфигурации читать из каталога поставки/упакованных ресурсов.
- Изменяемые данные по умолчанию: `%LOCALAPPDATA%\JudgingApp\` с подкаталогами `data`, `backups`, `logs`, `exports`.
- Не зависеть от текущей рабочей директории ярлыка; не писать в `Program Files` или каталог временной распаковки.
- Предусмотреть выбор постоянного каталога данных; переносной режим включается явно и требует доступной для записи папки.
- Обновление программы не удаляет данные; миграция базы предваряется backup. Повторная установка открывает прежнюю базу.

### 8.5. Воспроизводимая сборка

- Зафиксировать совместимые версии Python, Streamlit, PyInstaller, qrcode и остальных зависимостей; существующую чужую `.venv` не распространять.
- Сборку Windows x64 выполнять на Windows в чистом окружении.
- В репозитории предоставить `requirements.txt` либо `pyproject.toml` с lock-файлом, `Judging.spec`, `build.ps1`, `launcher.py` и инструкцию релиза.
- Включить в spec нужные метаданные, ресурсы и статические файлы Streamlit. Изолировать обращения к внутреннему bootstrap API и проверить их на закреплённой версии; не считать совместимость гарантированной для будущих обновлений.
- Не включать реальную базу мероприятия, токены и пароли в установочный пакет. Поставлять пустую базу либо создавать её при запуске.
- Целевая ОС: Windows 10/11 x64; проверить обе заявленные платформы без установленного Python, включая путь и имя пользователя с кириллицей.
- Зафиксировать фактические время запуска и размер сборки. Цель запуска на согласованном тестовом ноутбуке — до 30 секунд; при превышении показывать прогресс и документировать результат.

## 9. Архитектура и документация

Разделить код по ответственности: UI, права, хранилище/миграции, расчёт, экспорт, конфигурация и запуск. Конкретные имена модулей выбирает разработчик. Обработка ошибок не должна оставлять ложное сообщение об успешной записи.

Обновить инструкцию организатора: первый запуск, сеть, регистрация судей, оценивание, закрытие, CSV, backup, восстановление, перенос и остановка. Удалить из документации неподтверждённые утверждения о нагрузке и исправить описание защиты доступа. Добавить журнал версий и описание известных ограничений.

## 12. Решения для утверждения перед зависимой реализацией

| Вопрос | Предлагаемое решение |
|---|---|
| Расчёт новых событий | Усечение отдельно по критериям при пяти и более допустимых оценках |
| Округление | Конечный результат до 0,01; правило half-up, без промежуточного округления |
| Равенство | Общие места 1, 2, 2, 4 по конечному округлённому результату |
| Пропуски и самоотвод | Явный состав ожидаемых судей для каждой работы; исключения с причиной; минимум допустимых оценок задаётся регламентом |
| Дифференциация работ | Уточнить отдельно тип по содержанию и категорию учебная/конкурсная/ВКР; утвердить максимумы, особенно для критериев 2, 3, 6 |
| Штрафы | До утверждения шкалы отключены; согласовать основания, величины и нижнюю границу итога |
| Порог обсуждения | Относительный разброс по критерию; численное значение определить на пилоте |
| Видимость секретарю | Числа доступны после закрытия, до него только статусы |
| Отправка карточек | Судья отправляет по каждой работе; открытие правки только секретарём |
| Windows-поставка | В первой версии `onedir` с одним запускаемым EXE внутри папки; `onefile` после проверки |

Неопределённость методики не препятствует реализации хранения, CSV и лаунчера: интерфейсы расчёта и настройки проектировать заранее, но официальный расчёт не выбирать молча.
