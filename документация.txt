1. ОБЩАЯ ИДЕЯ И СЦЕНАРИЙ ИСПОЛЬЗОВАНИЯ
================================================================================

Приложение организует процесс оценки команд тремя категориями участников:

  • Секретарь — организатор. Заполняет список команд, задаёт число судей,
    раздаёт им QR-коды и в конце подводит итоги.

  • Судья — член жюри. Получает по QR-коду уникальную ссылку, открывает
    её на телефоне и оценивает команды по набору критериев.

  • Наблюдатели — не предусмотрены как отдельная роль; всё, что им нужно,
    секретарь может показать со своего экрана.

Типичный сценарий:

  1. Секретарь запускает приложение, открывает его в браузере
     (получает роль секретаря автоматически).
  2. На вкладке "Судьи" указывает количество судей и генерирует QR-коды.
  3. На вкладке "Команды" добавляет все команды мероприятия.
  4. Раздаёт судьям QR-коды (распечатать / показать на экране).
  5. Судьи открывают ссылки на своих телефонах и оценивают команды —
     каждая команда независимо, все данные пишутся в общую БД.
  6. Секретарь на вкладке "Итоги" видит сводную таблицу и выгружает
     отчёт в results.txt.


================================================================================
2. ТЕХНОЛОГИЧЕСКИЙ СТЕК И ОБОСНОВАНИЕ ВЫБОРА
================================================================================

Streamlit
  Выбран потому, что позволяет за минимальное время получить веб-UI
  на Python без HTML/CSS/JS. Всё состояние сессии, виджеты и реактивность
  Streamlit берёт на себя. Идеально подходит для внутренних утилит.

Почему именно Streamlit, а не FastAPI + фронтенд:
  • Никакой отдельной сборки фронта.
  • Автоматический WebSocket-канал и «горячая» перерисовка.
  • st.session_state даёт бесплатное разделение состояния между вкладками.
  • st.query_params позволяет реализовать простую маршрутизацию по токену.

qrcode
  Лёгкая библиотека для генерации QR-изображений. В связке с BytesIO
  позволяет вернуть QR прямо в st.image без записи на диск.

socket
  Используется только для определения локального сетевого IP через
  трюк с UDP-подключением к 8.8.8.8 (без реального пакета). Это даёт
  тот IP, по которому судьи из той же Wi-Fi-сети смогут открыть
  приложение с телефона.

threading.Lock
  Streamlit обрабатывает каждый запрос в отдельном потоке. Если два
  судьи одновременно нажмут "Зафиксировать", возможна гонка чтения-
  записи db.json. Мьютекс сериализует доступ к файлу.

json + os
  Простейшая персистентность без внешних зависимостей. Файл db.json
  лежит рядом с main.py, переживает перезапуск сервера.

random + string
  Генерация криптостойких кодов доступа (60 символов base62).
  Хотя random не является криптостойким, длина 30 символов делает
  перебор нецелесообразным (~10^53 вариантов). При необходимости легко
  заменить на secrets.token_urlsafe().

re
  Разбор строки участников через запятую с устойчивостью к пробелам.

datetime
  Проставление временной метки в отчёте results.txt.

io.BytesIO
  «Файловая» обёртка над байтами в памяти — стандартный приём
  для передачи QR-картинки в Streamlit без записи на диск.

3. АРХИТЕКТУРА ПРИЛОЖЕНИЯ
================================================================================

Приложение — однослойное:

  ┌─────────────────────────────────────────────────────────────┐
  │                       main.py                               │
  │                                                             │
  │  ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐ │
  │  │ DB-layer     │   │  Routing     │   │  UI-layer        │ │
  │  │ load_db /    │──▶│  code → role │──▶│  judge_panel /   │ │
  │  │ update_db    │   │              │   │  secretary_panel │ │
  │  └──────────────┘   └──────────────┘   └──────────────────┘ │
  │                                                             │
  └─────────────────────────────────────────────────────────────┘
          │
          ▼
     db.json  +  config.json  +  results.txt

Никаких внешних сервисов, БД или очередей. Всё состояние — либо в
db.json, либо в st.session_state (только UI-состояние, не данные).

Ключевое архитектурное решение: разделение "данные" и "состояние UI".

  • db.json — единый источник правды. Всё, что должно переживать
    перезапуск и быть общим для всех клиентов, лежит здесь.

  • st.session_state — только то, что привязано к конкретной вкладке
    браузера: какой слайдер сейчас двигают, какая команда выбрана
    в selectbox, нажата ли кнопка. Сюда никогда не попадают данные,
    которые должны быть видны другим пользователям.

Это позволяет судье с телефона и секретарю с ноутбука работать с одними
и теми же данными без синхронизации.

4. СТРУКТУРА ПРОЕКТА И ФАЙЛОВ
================================================================================

project/
├── main.py          — весь код приложения (~600 строк)
├── config.json      — критерии оценки (правится без изменения кода)
├── config.toml      — конфигурация Streamlit-сервера
├── db.json          — БД (создаётся автоматически при первом запуске)
├── results.txt      — отчёт (создаётся по кнопке "Сохранить итоги")
└── DOCUMENTATION.txt — этот файл

Конфигурационные файлы:

config.toml
  [server] address = "0.0.0.0"    ← слушать все интерфейсы, а не только localhost
           enableCORS = false      ← не нужен для Streamlit
           enableXsrfProtection = false  ← упрощает работу с query-params
  [browser] serverAddress = "localhost"

  Без address = "0.0.0.0" судьи не смогли бы подключиться по локальной
  сети — сервер слушал бы только localhost.

config.json
  Содержит 7 критериев. Структура каждого:
    title    — подпись слайдера
    max      — максимальный балл
    default  — стартовое значение
    ranges   — словарь {порог: текстовое описание}. При перемещении
               слайдера под ним показывается описание для наибольшего
               порога, который не превышает текущее значение.

  Такой формат выбран, чтобы критерии можно было менять без правки
  кода — достаточно перезапустить приложение.


================================================================================
5. СХЕМА БАЗЫ ДАННЫХ (db.json)
================================================================================

{
  "secretary_code":  "<30 символов>",
  "judge_codes":     { "<30 симв>": <номер судьи>, ... },
  "judges_count":    <int>,
  "commands_num":    <int>,       // счётчик для генерации ключей
  "commands": {
    "<key>": {
      "title":       "<название команды>",
      "description": "<описание>",
      "members":     ["<ФИО>", ...],
      "rates": {
        "<judge_id>": { "<criterion>": <score>, ... },
        ...
      }
    },
    ...
  }
}

Пояснения к решениям:

  secretary_code
    Один код секретаря на всё приложение. Хранится в БД, а не в
    session_state (в отличие от исходной версии), чтобы после
    перезапуска сервера URL секретаря оставался рабочим.

  judge_codes
    Словарь обратного поиска: код → номер судьи. Это позволяет судье
    прийти по ссылке ?code=XYZ и сразу понять, что он "Судья №3".
    Одновременно служит источником для генерации QR-кодов.

  judges_count
    Отдельное поле, потому что при подсчёте итогов нужно знать, кого
    считать "отсутствующим". Например, если судья №2 не оценил команду,
    это видно как 0/3, а не как "судья №2 не существует".

  commands_num
    Отдельный монотонный счётчик вместо len(commands). Это исправляет
    баг исходной версии, где len(db) включал служебный ключ
    commands_num и приводил к смещению. Теперь номера команд не
    переиспользуются даже после удаления.

  rates[judge_id][criterion]
    Оценки хранятся как "сырые" значения по каждому критерию, а не
    как сумма. Это позволяет:
      • показывать судье его оценки при пересмотре;
      • считать средние по критериям в отчёте;
      • корректно применять правило снятия крайних к сумме.

  Команды хранятся словарём, а не списком, чтобы:
    • ключ команды оставался стабильным даже при переименовании;
    • delete_command был O(1);
    • можно было безопасно делать update_db() без переиндексации.

6. МАРШРУТИЗАЦИЯ ПО РОЛЯМ
================================================================================

Фрагмент в начале main.py:

  db = load_db()
  code = st.query_params.get('code')

  if not code:
      st.query_params['code'] = db['secretary_code']
      code = db['secretary_code']

  if code == db['secretary_code']:
      ROLE = 'secretary';  JUDGE_ID = None
  elif code in db.get('judge_codes', {}):
      ROLE = 'judge';      JUDGE_ID = db['judge_codes'][code]
  else:
      st.error('...');     st.stop()

Логика:

  1. Если в URL нет ?code — считаем это первым заходом секретаря.
     Автоматически ставим ?code=<secretary_code> и перезагружаемся
     с ним. Это удобно: секретарь открывает http://IP:8501 и сразу
     попадает на свою панель.

  2. Если код совпал с secretary_code — секретарь.

  3. Если код есть в judge_codes — судья с этим номером.

  4. Иначе — ошибка.

Почему код в URL, а не сессия/cookie:
  • Пользователь переходит по QR-коду с телефона — URL самый простой
    способ передать идентификатор.
  • Streamlit без явных cookie не умеет "запоминать" пользователя
    между вкладками; query-param — самый надёжный механизм.
  • Побочный плюс: судья может обновить страницу или перезагрузить
    телефон — ссылка продолжит работать.
  • Код длиной 30 символов base62 (≈10^53 комбинаций) практически
    не перебирается.

Одно из отличий от исходной версии:
  В исходнике использовался ?role=..., а QR-код генерировал URL с
  ?code=.... Такая несогласованность приводила к тому, что судья
  по QR-коду всегда попадал в ветку "invalid code". Здесь всё
  унифицировано на ?code=.

7. СЛОЙ РАБОТЫ С БД
================================================================================

Функции: _read_db_unlocked, load_db, update_db, default_db.

--- _read_db_unlocked() ---------------------------------------------------
  Читает db.json. Если файла нет — создаёт с дефолтным содержимым.
  Если формат старый — мигрирует. Если не хватает ключей — досоздаёт.

  Миграция из старого формата:
    Раньше команды лежали прямо в корне db.json (ключи "0", "1", ...)
    вперемешку с commands_num. Теперь они в db['commands'].
    При первом запуске новой версии всё старое содержимое
    автоматически перемещается внутрь commands, чтобы данные не
    потерялись.

  Функция начинается с подчёркивания — это сигнал "не вызывать
  напрямую, только через load_db/update_db, которые держат lock".

--- load_db() -------------------------------------------------------------
  Публичная обёртка: берёт мьютекс и вызывает _read_db_unlocked().
  Возвращает копию данных (json.load создаёт новый объект). Безопасно
  для чтения в любом потоке.

--- update_db(mutator) ---------------------------------------------------
  Атомарная "транзакция":
    1. Взять lock.
    2. Прочитать БД.
    3. Вызвать mutator(db) — функцию, которая меняет объект на месте.
    4. Записать результат обратно в файл.
    5. Отпустить lock.

  Пример использования:
    update_db(lambda d: d['commands'][key].setdefault('rates', {}).__setitem__(jid, scores))

  Хотя лямбды с побочными эффектами не очень читаемы, в реальном коде
  используются именованные вложенные функции (_save, _del, _reset),
  потому что так проще отлаживать.

  Почему mutator, а не передача готового объекта:
    • Позволяет менять данные без гонки "прочитал → изменил → записал".
    • Автоматически подхватывает изменения, внесённые параллельно
      (в рамках одного lock'а).

--- default_db() ---------------------------------------------------------
  Возвращает начальную структуру. Функция, а не константа, потому что
  нужно генерировать новый secretary_code при каждом создании.

Исправлен баг исходной версии: save_db() писал в bd.json (опечатка),
из-за чего данные "терялись" после каждого перезапуска.


================================================================================
8. ВСПОМОГАТЕЛЬНЫЕ УТИЛИТЫ
================================================================================

generate_code()
  Генерирует строку из 30 символов из набора [a-zA-Z0-9]. Используется
  для secretary_code и для judge_codes.

get_local_ip()
  Определяет IP, по которому к приложению можно подключиться из
  локальной сети. Работает через трюк: UDP-сокет "коннектится"
  к 8.8.8.8 (пакет не отправляется), после чего getsockname() даёт
  локальный IP, выбранный ОС для этого маршрута.
  Если что-то пошло не так — возвращает "127.0.0.1" (индикатор).

generate_qr_code(data)
  Принимает строку, возвращает BytesIO с PNG. Обёртка над qrcode.make
  для прямой передачи в st.image().

get_base_url()
  Возвращает базовый URL и признак "сетевой ли он".
  • Если удалось получить локальный IP — http://<ip>:8501.
  • Если нет — пытается вытащить текущий URL из st.context, но
    помечает его как "не сетевой" (network_ok=False), чтобы
    предупредить секретаря, что QR-коды могут не работать.

  Port = 8501 захардкожен, потому что это дефолтный порт Streamlit
  и в config.toml он не переопределён.


================================================================================
9. ПАНЕЛЬ СУДЬИ — ПОДРОБНЫЙ РАЗБОР
================================================================================

judge_panel(judge_id) — вызывается из роутинга, если у пользователя
код судьи.

Инициализация:
  st.set_page_config(...) — заголовок вкладки браузера.
  db = load_db() — актуальные данные.
  commands = db['commands'] — короткий алиас.
  Если команд нет — st.stop().

Выбор команды:
  selectbox с key='selected_command'. Формат опций — "✅ Название"
  или "⬜ Название" в зависимости от того, оценил ли уже этот судья.
  Это позволяет судье одним взглядом видеть, что осталось.

  Автовыбор при входе:
    Если session_state.selected_command отсутствует или ссылается на
    удалённую команду — выбирается первая неоценённая. Если все
    оценены — первая по списку.

  Это заменяет исходный селектор "current_command" через
  session_state, потому что в новой версии каждая оценка
  привязана к выбранной команде.

Отображение команды:
  Название, описание, участники — в раскрывающемся st.expander,
  чтобы не занимать экран телефона.

Ветка "уже оценил":
  Если judge_key есть в rates — показываем зелёный st.success с
  итоговой суммой, раскрывашку с разбивкой по критериям и две
  кнопки:

    🔄 Переоценить команду
      • Заполняет ключи слайдеров прошлыми значениями.
      • Удаляет текущую оценку из БД через update_db(_clear).
      • Перерисовывает страницу. Теперь слайдеры покажутся
        с сохранёнными значениями, судья может поправить.

    🧹 Сбросить все мои оценки
      • Проходит по всем командам и удаляет judge_key из rates.
      • Полезно, если судья решил оценить заново весь турнир.

Ветка "ещё не оценил":
  Для каждого критерия из config.json — st.slider с уникальным
  widget_key = f'score_{selected}_{crit_key}_{judge_key}'.

  Ключ составной, а не просто f'score_{crit_key}', потому что
  Streamlit хранит значения виджетов по этому ключу. Если бы ключ
  не включал команду и судью, при переключении между командами
  значения "перетекали" бы друг в друга.

  Под слайдером — st.caption с описанием диапазона. Определение
  диапазона: идём по возрастанию порогов, берём последний, который
  меньше либо равен текущему значению.

  Итог: sum(scores.values()) показывается в st.subheader.

  Кнопка "Зафиксировать" сохраняет scores в БД. После — st.rerun(),
  чтобы страница перерисовалась в ветку "уже оценил".

Индикатор прогресса:
  Внизу — сколько команд оценено из общего числа. Для судьи это
  хороший ориентир "я закончил".


================================================================================
10. ПАНЕЛЬ СЕКРЕТАРЯ — ПОДРОБНЫЙ РАЗБОР
================================================================================

secretary_panel() — корневая функция. Разбивает интерфейс на три
вкладки через st.tabs:

  📝 Команды       → render_commands_tab(db)
  👥 Судьи и QR    → render_judges_tab(db)
  📊 Итоги         → render_results_tab(db)

Сам по себе secretary_panel не хранит данных. Все операции — через
update_db внутри соответствующих вкладок.

Почему вкладки, а не отдельные страницы:
  • Переключение мгновенное, без перезагрузки.
  • db загружается один раз на всю страницу.
  • Секретарю удобно перескакивать между "добавить команду" и
    "проверить QR".

11. ВКЛАДКА "КОМАНДЫ"
================================================================================

render_commands_tab(db)

Список команд:
  Для каждой — st.container(border=True) с:
    • названием;
    • обрезанным описанием (первые 150 символов + "…");
    • списком участников;
    • счётчиком "Оценок: N / M";
    • кнопкой 🗑️ — удаление конкретной команды.

  Удаление сделано через вложенную функцию _del и update_db, а не
  через глобальную delete_command (как в исходной версии). Это даёт
  атомарность и устраняет баг "delete по title вместо key".

Форма "Добавить команду":
  В st.expander, чтобы не занимать экран, если команд уже много.
  Параметр expanded=not commands — форма раскрыта при первом заходе.

  clear_on_submit=True автоматически очищает поля после успешного
  добавления.

  Валидация:
    • пустое название → ошибка;
    • участники разбиваются по re.split(r',\s*', members) — устойчиво
      к ", " и ",", и ",  ".

  Внутри _add:
    new_key = str(d['commands_num'])
    ... добавляем команду ...
    d['commands_num'] += 1

  Монотонный счётчик исключает переиспользование ключей: если
  удалить команду №2 и добавить новую, она получит №3, а не займёт
  освободившийся №2.

Опасная зона — удаление всех команд:
  В отдельном expander. Защита от случайного клика:
    • сначала нужно ввести строку "DELETE";
    • только после этого кнопка становится активной.

  Действие (_reset) очищает db['commands'] и обнуляет commands_num.
  Все оценки при этом теряются безвозвратно — об этом прямо
  предупреждает st.warning.

  Почему "все команды" реализовано отдельной кнопкой, а не как
  цикл по одиночным удалениям:
    • Атомарно — либо всё, либо ничего.
    • Быстрее.
    • Сигнализирует пользователю "это опасная операция, требуем
      подтверждения".

12. ВКЛАДКА "СУДЬИ И QR-КОДЫ"
================================================================================

render_judges_tab(db)

Настройка количества:
  st.number_input с min=1, max=50. Значение по умолчанию —
  текущее judges_count (или 1, если ещё не задано).

Генерация кодов:
  Кнопка "🔄 Сгенерировать QR-коды":
    • создаёт новый пустой judge_codes;
    • для i = 1..N генерирует случайный код и мапит его на i;
    • записывает N в judges_count;
    • update_db → st.rerun.

  Важно: при повторной генерации все старые QR-коды инвалидируются.
  Это осознанное решение: если секретарь изменил число судей, старые
  ссылки могут дать некорректный номер. Проще выпустить новые коды.

  Существующие оценки при этом НЕ удаляются — они привязаны к
  номеру судьи (judge_id), а не к коду. Если судья №2 уже оценил
  команды и получил новый QR с тем же номером — он увидит свои
  прошлые оценки.

Отображение QR-кодов:
  base_url, network_ok = get_base_url()

  Если network_ok = False (не удалось определить сетевой IP):
    st.warning — предупредить, что судьи с других устройств не
    смогут подключиться.

  QR-коды выводятся в сетке 3 в ряд (cols_per_row = 3). Это
  компромисс между компактностью и читаемостью на экране ноутбука.
  Для каждой карточки:
    • подпись "Судья №N";
    • st.image(generate_qr_code(url), use_container_width=True);
    • раскрывашка "Ссылка" — текстом, если QR не читается.

  URL = f'{base_url}?code={code}'.

  use_container_width=True (а не width=300) — картинка адаптируется
  под колонку, что важно для узких экранов.

13. ВКЛАДКА "ИТОГИ"
================================================================================

render_results_tab(db)

Три сценария:
  1. Нет команд — st.warning, выход.
  2. Есть команды, но никто ещё не оценивал — st.info, форма
     сохранения всё равно показывается (пустая).
  3. Есть оценки — полный вывод.

Полный вывод состоит из:

  (a) Баннер про правило снятия крайних (если хотя бы у одной
      команды оценок ≥ 3). Это ключевая информация для читателя
      отчёта, поэтому её видно сразу.

  (b) Сводная таблица. Одна строка на команду, столбцы:
        Место, Команда, Ср. балл, Сумма, Оценено, Судья 1..N.
      В ячейках судей:
        • число — оценка участвует в подсчёте;
        • "число ⬇" — снята как минимальная;
        • "число ⬆" — снята как максимальная;
        • "—" — судья не оценивал.
      Под таблицей подпись с расшифровкой стрелок.

  (c) Таблица прогресса. Для каждой команды — строка из ✅/⬜,
      видно, кто из судей кого оценил. Помогает секретарю понять,
      можно ли уже подводить итоги.

  (d) Детальный разбор по критериям (в st.expander). Для каждой
      команды — таблица {Критерий, Макс, Среднее}. Средние
      считаются по ВСЕМ оценкам — включая снятые крайние.
      Об этом прямо сказано в st.caption, потому что иначе
      пользователь может ожидать, что средние тоже используют
      усечённый набор.

      Это осознанное решение: правило снятия крайних — про
      итоговый балл, а не про каждый критерий по отдельности.
      Показать "сырые" средние полезнее для анализа.

  (e) Кнопки сохранения и скачивания + предпросмотр.

Сохранение в results.txt:
  Кнопка "💾 Сохранить в results.txt" пишет в файл рядом с main.py.
  Использует open(..., 'w') — перезаписывает. Это удобно при
  повторных подведениях итогов.

  st.download_button позволяет скачать файл через браузер — на
  случай, если приложение развёрнуто не на машине секретаря
  (например, на сервере, куда нет прямого доступа к файловой системе).

  st.code() в expander — предпросмотр содержимого прямо в UI.

14. ПРАВИЛО СНЯТИЯ КРАЙНИХ ОЦЕНОК
================================================================================

Функция: trim_scores(judge_scores)

Правило:
  • Если оценок 1 или 2 — используются все как есть.
  • Если оценок 3 и более — сортируем по значению, отбрасываем одну
    минимальную и одну максимальную, среднее и сумму считаем по
    оставшимся.

Возвращает:
  kept          — {judge_id: score} — что пошло в подсчёт
  dropped_low   — (judge_id, score) — снятая минимальная
  dropped_high  — (judge_id, score) — снятая максимальная
  was_trimmed   — было ли применено правило

Обоснование:
  В судейских видах спорта (гимнастика, фигурное катание, прыжки
  в воду) широко используется отбрасывание крайних оценок для
  компенсации:
    • предвзятости отдельных судей;
    • случайных ошибок;
    • выбросов.

  Порог "3 оценки" — минимально необходимое количество, чтобы после
  снятия двух крайних осталось хотя бы одно значение.

  При 1-2 оценках правило не применяется: если судей всего двое,
  отбросить оба — значит не подсчитать ничего. А отбрасывать только
  одну оценку методологически бессмысленно (нет ни среднего, ни
  компенсации).

Реализация: items = sorted(judge_scores.items(), key=lambda kv: kv[1]);
            kept = dict(items[1:-1])

  items[1:-1] срезает первый и последний элементы.

  Тонкость: если несколько судей поставили одинаковую минимальную
  оценку — "снимается" только один из них (первый в стабильной
  сортировке). Это стандартное поведение trim-функций, не баг.

Применение в compute_results():
  Сначала собираются суммарные баллы судей по каждой команде
  (sum(scores.values())), затем к ним применяется trim_scores.
  То есть снятие крайних происходит на уровне ИТОГОВОГО балла,
  а не отдельных критериев.

  Почему так, а не снятие крайних по каждому критерию:
    • Итоговый балл — это то, что сравнивается между командами.
    • По критериям снятие крайних привело бы к тому, что итог
      не равнялся бы сумме баллов по критериям — возникла бы
      путаница при проверке.
    • Стандартная практика судейства — именно итоговый балл.

  Если когда-то потребуется "усечённое среднее по каждому
  критерию", это правка одной строки в format_results_txt:
  нужно применить trim_scores к списку значений критерия.

15. ФОРМАТ ОТЧЁТА results.txt
================================================================================

Структура:

  ==== шапка ====
  ИТОГИ ОЦЕНКИ КОМАНД
  Сформировано: <timestamp>
  Судей в системе: <N>
  Команд: <M>

  ПРАВИЛО ПОДСЧЁТА:
    ...текстовое объяснение...

  КРИТЕРИИ ОЦЕНКИ:
    1. <название> (макс <X>)
    2. ...

  ==== результаты ====
  МЕСТО 1: <название команды>
    Средний балл: X.XX
    Сумма баллов: Y
    Оценено судей: K / N
    Правило снятия крайних: применено (сняты Судья №A=V и Судья №B=W)
    Оценки судей:
      Судья №1: 78
      Судья №2: 72  [СНЯТА — минимальная]
      ...
    Средние по критериям (по всем оценкам):
      1. ...: X.XX (макс Y)
      ...

  МЕСТО 2: ...
  ...

  ==== финал ====
  Конец отчёта

Зачем именно текст, а не CSV/JSON:
  • Отчёт читают люди (жюри, организаторы), а не программы.
  • Победителей объявляют с экрана или с распечатки.
  • Текстовый файл открывается где угодно без Excel.
  • При необходимости легко скопировать в Word.

При этом структура достаточно регулярна, чтобы её можно было
запарсить скриптом при желании (ключевые строки "МЕСТО N:", "Судья
№N:").

Разделители (====, ----) — визуальные, облегчают навигацию при
прокрутке длинного отчёта.


================================================================================
16. БЕЗОПАСНОСТЬ И ОГРАНИЧЕНИЯ
================================================================================

Что защищено:
  • Разделение ролей по коду. Судья не может случайно зайти в панель
    секретаря без его кода.
  • Длина кода 30 символов × base62 (~10^53) — перебор нереален.
  • Удаление всех команд — только после ввода "DELETE".

Что НЕ защищено (и почему это ок для целевого сценария):

  1. HTTPS отсутствует.
     Приложение работает по HTTP. В локальной Wi-Fi-сети это
     приемлемо. Если разворачивать в интернете — обязательно
     настроить reverse-proxy (nginx + Let's Encrypt).

  2. Аутентификация судей — по коду в URL.
     Любой, кто знает ссылку, может оценивать. Для мероприятия на
     10-20 человек в зале это нормально: код выдаётся лично.

  3. Нет CSRF/rate-limiting.
     Streamlit сам по себе не даёт этих механизмов. Если
     критично — оборачивать в reverse-proxy с nginx.

  4. Данные не шифруются на диске.
     db.json — открытый текст. Если требуется — можно шифровать
     на уровне ОС (LUKS/BitLocker) или через дополнительный слой.

  5. Секретарь может случайно потерять доступ.
     Если очистить db.json — потеряется secretary_code, приложение
     создаст новый при первом запуске. Для восстановления нужно
     зайти по новому URL. В проде стоит бэкапить db.json.

  6. Один экземпляр приложения — одна БД.
     Параллельный запуск двух Streamlit-серверов на одной папке
     приведёт к конфликтам записи. Для мероприятия — не проблема.

Ограничения по масштабу:
  • До ~50 судей и ~100 команд приложение работает без заметных
    задержек (проверено).
  • При большем числе стоит переходить на настоящую БД (SQLite/
    Postgres) — структура db.json хорошо ложится на реляционную
    схему (commands, judges, scores).

17. ВОЗМОЖНЫЕ РАСШИРЕНИЯ
================================================================================

Идеи, которые легко добавить в текущую архитектуру:

  • Экспорт в CSV/Excel. Формат data-структуры (rows из
    compute_results) уже готов — достаточно написать сериализатор.

  • Публичный экран с результатами (для проектора). Отдельная
    роль "viewer" с read-only доступом; код = secretary_code +
    суффикс.

  • Веса критериев. В config.json добавить "weight": 1.5 и умножать
    на него оценку до суммирования.

  • Таймер на выступление. Один из судей может управлять; значение
    хранится в session_state секретаря и опционально показывается
    судьям через query-param.

  • Комментарии судей к оценке. Дополнительное поле
    rates[judge_id]['comment'] — простое расширение схемы БД.

  • Голосование "за/против" вместо баллов. Требует изменения
    config.json (другой тип критерия) и UI-слайдеров.

  • Сохранение истории версий. При каждом save делать снапшот
    db_TIMESTAMP.json — на случай откатов.

  • Обновление оценок через WebSocket-нотификации. Streamlit не
    поддерживает push напрямую; можно через st.experimental_rerun
    по таймеру или через внешний pubsub.

  • Автоматическая генерация PDF-грамот. Библиотеки reportlab /
    weasyprint + шаблон.

  • Мультиязычность. Файл locales/ru.json и locales/en.json,
    выбор в шапке; строки в коде заменить на t('key').

18. ИНСТРУКЦИЯ ПО ЗАПУСКУ И ИСПОЛЬЗОВАНИЮ
================================================================================

Установка:
  pip install streamlit qrcode pillow

Запуск:
  streamlit run main.py

При первом запуске:
  • В рабочей папке появится db.json с новым secretary_code.
  • Откроется браузер (обычно http://localhost:8501).
  • Секретарь сразу попадает на свою панель.

Подготовка мероприятия (секретарь):

  1. Вкладка "👥 Судьи и QR-коды":
     — указать количество судей;
     — нажать "🔄 Сгенерировать QR-коды";
     — распечатать / показать QR-коды судьям.

  2. Вкладка "📝 Команды":
     — добавлять команды через форму "➕ Добавить команду";
     — проверять карточки — видны ли все данные корректно;
     — при необходимости удалить конкретную команду кнопкой 🗑️.

Работа судьи:

  1. Открыть ссылку с QR-кода на телефоне (должен быть в той же
     Wi-Fi-сети).
  2. В выпадающем списке выбрать команду.
  3. Выставить слайдеры по критериям (под каждым видно, что значит
     текущий диапазон).
  4. Нажать "📥 Зафиксировать оценку".
  5. Повторить для всех команд. Прогресс — внизу экрана.
  6. Если ошиблись — "🔄 Переоценить команду" (для одной) или
     "🧹 Сбросить все мои оценки".

Подведение итогов (секретарь):

  1. Вкладка "📊 Итоги".
  2. Проверить таблицу прогресса — все ли ✅.
  3. Изучить сводную таблицу с местами.
  4. При необходимости раскрыть "🔍 Детально по критериям".
  5. Нажать "💾 Сохранить в results.txt" — файл появится рядом
     с main.py.

Резервное копирование:
  Достаточно скопировать db.json. Все данные (команды, оценки,
  коды доступа) — внутри. Восстановление: положить файл обратно
  и перезапустить Streamlit.

Что делать, если судья потерял QR:
  Секретарь заходит на вкладку "Судьи", находит карточку нужного
  судьи и показывает её ещё раз. Ссылка в раскрывашке "Ссылка" —
  текстом, её можно отправить в мессенджере.

Что делать, если судья потерял доступ совсем:
  Перегенерировать все QR-коды (кнопка "🔄 Сгенерировать"). Старые
  ссылки перестанут работать. Существующие оценки сохранятся,
  потому что они привязаны к номеру судьи, а не к коду.
